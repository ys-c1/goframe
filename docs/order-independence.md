# 同帧指令顺序与末态哈希：可交换性证明与实验记录

实验代码：`api/order_test.go`；分组实现：`api/group.go`；分组记录：`artifacts/grouping-record.json`。
实验参数：`Bodies=4, SubSteps=4, Gravity=2`，首帧施加指令后再空跑 3 帧，共 4 帧。

## 1. 模型与记号

把状态看作 4n 维向量 `s = (posX, posY, velX, velY)`（每实体 4 个 Q16.16 槽）。
一条指令 `c = (Body=b, PushX, PushY)` 经 `Step` 施加的变换为 `T_c`：

```
T_c(s) = s + δ_c
```

`δ_c` 是常向量，仅在实体 `b` 的 `velX`、`velY` 两槽非零（`sim.State.Push`，internal/sim/sim.go:28）。
`Integrate` 与 `hash.State` 都不读取指令序列，只是状态的确定函数。

## 2. 引理与定理（对本内核成立的真实命题）

**引理 1（Push 是平移）。** 任意指令 `c` 的变换 `T_c` 是状态空间上的平移，且只写目标实体的速度槽。∎（由 Push 定义直接读出）

**引理 2（定点加法可交换、可结合）。** `fixed.Value` 的 `Add` 即 int32 加法。Go 规范规定有符号整数溢出结果由表示法确定（所有 Go 平台均为二进制补码，等价于模 2^32 加法），不发生 panic，也不允许编译器假设不溢出。模加法满足交换律与结合律。∎

**定理 1（同帧指令无条件可交换）。** 对同一帧内任意两条指令 `a, b`（无论目标是否相同）：

```
T_a ∘ T_b (s) = s + δ_a + δ_b = s + δ_b + δ_a = T_b ∘ T_a (s)   （引理 1、2）
```

**推论 1（顺序无关）。** 同一帧指令序列的任意排列产生相同的末态，进而产生相同的末态哈希。分组、交错、组内换序均不改变结果。

**推论 2（对用户命题的证伪）。** "同一实体的指令不可交换""可交换的充要条件是目标集合不相交"在本内核中**不成立**：可交换性是无条件的。实验证据见第 5 节，所有差值均为 0。

## 3. 用户命题在什么内核中才成立（一般化理论）

用户描述的命题对应的是**非平移指令**的内核。设指令 `c` 的变换 `T_c` 写状态槽集合 `W(c)`：

- **不同实体可交换的充要条件**：`W(a) ∩ W(b) = ∅`（写集不相交）。充分性：两者作用在不相交的状态分量上，复合与顺序无关。必要性：若交集非空，总可构造在该分量上不可交换的指令对（如 `vel = clamp(vel+d)` 中两个方向相反的饱和冲量）。
- **同一实体不可交换**：当 `T_c` 含非线性（截断、取整、乘法、饱和、上限）时，同一写集上 `T_a ∘ T_b ≠ T_b ∘ T_a`。例如 `Push` 若改为 `vel = min(vel+d, Vmax)`，先加哪个冲量会改变饱和结果。

本内核的 `Push` 是纯加法平移，退化到"恒可交换"，故上述条件的分界线根本不会出现。

## 4. 分组定理与充要条件

**分组方案**（api/group.go `GroupCommands`）：按目标编号稳定分组，组间按编号升序，组内保持输入中的原始相对顺序。

**定理 2（分组后顺序无关的充要条件）。** 该方案保证"任意输入顺序都收敛到同一末态"当且仅当：

1. 分组键只取决于指令多重集本身（目标编号满足；若按"首次出现顺序"排组则不满足）；
2. 不同组的指令两两可交换（此时组的任意交错等价于组间拼接）；
3. 组内顺序是输入顺序的确定函数（原始相对顺序满足），且组内指令两两可交换或组内顺序被规范固定。

**证明。** 充分性：任取同一多重集的两个输入序列。由条件 1，二者分组结果逐组相同（多重集相同 ⇒ 每组多重集相同；由条件 3，组内序列相同）。两个输入都是该规范序列的重排，差异仅在组的交错方式与（可能的）组内顺序；由条件 2、3 这些差异不改变复合变换，故末态相同。必要性：若条件 2 失败，存在两组各一条指令不可交换，构造仅在这两条指令相对顺序上不同的两个输入即得不同末态；若条件 1 或 3 失败，同一多重集可映射到不同规范序列，顺序无关无从谈起。∎

**推论。** 本内核中条件 2、3 由定理 1 恒成立，故分组规范化是恒等变换级别的保险：它固定了规范序列，但任何顺序本来就得到同一末态。若未来内核引入第 3 节所述的非平移指令，本方案在"同组指令才可写同一实体"的约束下依然成立。

## 5. 实验记录（两组互测）

指令：A 组（实体 0）`a1=(100003,-65537)`、`a2=(-77777,131073)`；B 组（实体 1）`b1=(32771,-131072)`、`b2=(65539,9999)`（原始 Q16.16 值，含低位零头）。

| 变体 | 首帧指令序 | 末态哈希 |
|---|---|---|
| baseline-grouped | a1 a2 b1 b2 | `a60e4a42c14f5446` |
| swap-within-group-A | a2 a1 b1 b2 | `a60e4a42c14f5446` |
| swap-within-group-B | a1 a2 b2 b1 | `a60e4a42c14f5446` |
| interleaved | b1 a1 b2 a2 | `a60e4a42c14f5446` |

逐项比对（基线 vs 各变体），快照布局为每实体 4 槽 `posX,posY,velX,velY`（实体 0=A 组，实体 1=B 组）：

| 对比对 | 整体哈希差值 | A 组指纹 xor | B 组指纹 xor | 快照非零项（16 槽逐项） |
|---|---|---|---|---|
| baseline vs 组内换序 A | 0 | 0 | 0 | 0 |
| baseline vs 组内换序 B | 0 | 0 | 0 | 0 |
| baseline vs 交错 | 0 | 0 | 0 | 0 |

另有单对指令实验：异实体换序哈希 `6808b0126086f74e`（两侧相同），同实体换序哈希 `0d195b866db21891`（两侧相同）。

**结论：组内换序的差值为 0，而非用户预期的非零。** 这与定理 1 一致：本内核中同帧指令任意换序都不改变末态。"差值不得为零"的断言在本内核上不可能成立，任何得到非零差值的"验证"都只能是篡改了内核语义。

## 6. 若观测到换序后哈希变化，真正应排查的方向

1. **跨帧换序**：`Command.Tick` 目前不被 `Step` 校验（api/api.go:65），指令落在哪一帧完全由它在回放日志中的位置决定。两条指令若被分到不同帧，末态必然不同——这是帧同步中最常见的分歧来源，组内分组无法修复，应对 `Tick` 与当前帧号做校验。
2. 指令集合本身不同（丢指令、重复指令），而非顺序不同。
3. 内核被加入非平移操作（见第 3 节），此时本文件第 4 节的充要条件开始真正起作用。
